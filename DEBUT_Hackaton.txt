## 3. Problème et solution

Un étudiant possède une annale ou un document d'exercices au format PDF.

Le document contient des questions et leurs corrections, mélangées dans un même fichier.

Les corrections peuvent apparaître :

- Sous les questions.
- À côté des questions.
- Dans une autre colonne.
- Entre deux questions.
- Sous forme de réponses rédigées.
- Sous forme de réponses indiquées dans un QCM.
- Dans une partie distincte du document.

L'étudiant souhaite résoudre les questions sans voir les réponses.

**Unspoil est une PWA permettant de masquer automatiquement les corrections d'un PDF tout en conservant les questions visibles.**

Le document original doit conserver sa mise en page.

Nous ne voulons pas transformer le PDF en quiz, générer de nouveaux exercices ou reconstruire son contenu.

Nous voulons simplement rendre le PDF original utilisable pour un entraînement sans spoiler.

## 4. Fonctionnement exact du produit

### 4.1. Importation

L'utilisateur ouvre Unspoil et importe un PDF depuis son appareil.

Le logiciel est capable d'afficher ce PDF fidèlement.

Il traite son contenu afin d'identifier les questions et les éventuelles corrections.

### 4.2. Fonctionnalité principale : masquer les corrigés

L'utilisateur dispose d'un bouton principal :

**Masquer les corrigés**

Lorsqu'il clique sur ce bouton :

1. L'algorithme déterministe analyse le document.
2. Il identifie les régions correspondant probablement à des corrections.
3. Il recouvre ces régions avec des masques blancs opaques.
4. Les questions restent visibles.
5. Le document conserve sa mise en page originale.

Les masques ne doivent pas être des floutages.

Ils doivent être blancs et totalement opaques.

Chaque bloc de correction détecté possède un bouton :

**Afficher le corrigé**

Lorsque l'utilisateur clique dessus, seul le bloc de correction correspondant est révélé.

Les autres corrections restent masquées.

L'utilisateur doit également pouvoir remasquer le bloc.

Cette interaction doit être simple, sans configuration laborieuse.

### 4.3. Fonctionnalité de secours : révélation progressive

L'algorithme déterministe ne pourra pas reconnaître tous les formats de documents.

Nous avons donc besoin d'un mécanisme de secours indépendant de l'algorithme.

Son fonctionnement :

1. Le document est entièrement masqué par défaut.
2. Un trait horizontal délimite la partie visible et la partie masquée.
3. L'utilisateur fait glisser ce trait verticalement.
4. Le document apparaît progressivement au-dessus du trait.
5. Tout ce qui se situe en dessous reste couvert par un masque blanc opaque.

L'utilisateur peut déplacer le trait dans les deux sens.

Il doit pouvoir avancer progressivement dans le document sans apercevoir la suite.

Le mécanisme doit fonctionner :

- À la souris.
- Au tactile.
- Sur les documents multipages.
- Indépendamment du contenu du document.
- Même lorsqu'aucun texte n'est extractible.

Le mécanisme de secours doit être accessible manuellement, y compris lorsque l'algorithme automatique a produit un résultat imparfait.

Il ne dépend d'aucune détection sémantique.

### 4.4. Cas critique A : PDF contenant uniquement un sujet

Certains documents contiennent des questions, mais aucune correction.

Le logiciel doit, autant que possible, reconnaître ce cas.

Lorsqu'il dispose d'indices suffisants pour considérer qu'aucune correction n'a été détectée, il affiche :

**Aucun corrigé n'a été détecté.**

Il ne doit pas créer arbitrairement des masques sur les questions.

Attention : ne pas parvenir à identifier une correction n'est pas nécessairement équivalent à déterminer que le document est un sujet sans corrigé.

Il faut distinguer :

- Un document probablement constitué uniquement de questions.
- Un document dont la structure n'est pas reconnue.

Dans le second cas, proposer le mécanisme de secours plutôt que prétendre avoir reconnu un sujet sans corrigé.

### 4.5. Cas critique B : PDF contenant uniquement un corrigé

Certains documents contiennent uniquement la correction, sans les énoncés.

Le logiciel doit rester utile dans ce cas.

Il doit essayer de :

1. Identifier les différentes questions ou exercices à partir de leur numérotation et de la structure du corrigé.
2. Segmenter le corrigé en blocs.
3. Masquer initialement tous ces blocs.
4. Permettre de révéler indépendamment la correction de chaque question.

Si le découpage par question est impossible ou trop incertain, proposer la révélation progressive.

Il ne faut pas inventer les énoncés absents.

### 4.6. Cas critique C : document mixte non reconnu

Si le logiciel ne parvient pas à distinguer suffisamment les questions et les réponses :

- Il signale que la détection automatique est incertaine.
- Il propose le mécanisme de révélation progressive.
- Il ne prétend pas avoir correctement identifié toutes les corrections.

### 4.7. Protection contre l'affichage accidentel

Puisque l'objectif est d'éviter les spoilers, une proposition de comportement initial est de garder le document couvert pendant son importation et son analyse, jusqu'à l'action de masquage.

L'utilisateur doit pouvoir utiliser le mécanisme de secours sans avoir préalablement vu le document original.

Ce comportement initial doit être cohérent avec le parcours utilisateur et validé rapidement entre les trois membres.

## 5. Résumé des quatre configurations documentaires

| Configuration | Comportement attendu |
|---|---|
| Questions et corrections mélangées | Questions visibles, corrections masquées indépendamment |
| Sujet uniquement | Message « Aucun corrigé n'a été détecté » |
| Corrigé uniquement | Corrections masquées et découpées par question |
| Format non reconnu | Proposition du mode de révélation progressive |

Ces quatre configurations doivent guider la conception de l'algorithme, de l'interface et des tests.

## 11. Contrat technique initial proposé

Le contrat suivant constitue une base de départ pour les trois agents.

### Convention géométrique

Toutes les régions sont exprimées dans le repère canonique de leur page :

- Origine en haut à gauche.
- Axe x vers la droite.
- Axe y vers le bas.
- Coordonnées indépendantes du zoom.
- Dimensions de référence correspondant au viewport PDF à échelle 1.
- Rotation de la page prise en compte.
- Indices des pages commençant à zéro.

Proposition TypeScript :

```typescript
export interface Rect {
  x: number
  y: number
  width: number
  height: number
}

export interface TextItem {
  text: string
  bbox: Rect
  fontSize?: number
  fontName?: string
  hasEOL?: boolean
}

export interface PageData {
  pageIndex: number
  width: number
  height: number
  textItems: TextItem[]
}

export interface RasterData {
  width: number
  height: number
  rgba: Uint8ClampedArray
}

export interface DetectionInput {
  pages: PageData[]
  getRaster?: (
    pageIndex: number
  ) => Promise<RasterData>
}

export interface PageRegion {
  pageIndex: number
  bbox: Rect
}

export interface CorrectionBlock {
  id: string
  questionLabel?: string
  regions: PageRegion[]
}

export type DocumentKind =
  | 'mixed'
  | 'statement_only'
  | 'correction_only'
  | 'unknown'

export interface DetectionResult {
  kind: DocumentKind
  blocks: CorrectionBlock[]
  warnings: string[]
  needsFallback: boolean
}

export type DetectCorrections = (
  input: DetectionInput
) => Promise<DetectionResult>
```

Principes :

- Un bloc de correction peut contenir plusieurs rectangles.
- Un bloc peut s'étendre sur plusieurs pages.
- Le bouton de révélation concerne un bloc entier, et non nécessairement un rectangle individuel.
- Les données du détecteur ne dépendent pas de React.
- Le détecteur ne décide pas de la manière dont les boutons sont affichés.
- L'interface ne réimplémente pas l'algorithme de détection.
- Les régions sont converties en coordonnées écran uniquement pour leur affichage.
- Les données raster sont facultatives et peuvent être obtenues à la demande afin d'éviter de conserver toutes les pages en mémoire.
- Les informations réellement disponibles dans PDF.js doivent être vérifiées.
- Une information absente du PDF ne doit pas être inventée.

Le module PDF doit exposer un moyen de charger un fichier local, récupérer ses PageData, obtenir éventuellement le rendu raster d'une page et afficher une page dans un canvas.

Salif définit précisément cette interface avec Wael.

Les trois agents doivent utiliser une version unique du contrat après sa validation.

### 12.1. Objectif algorithmique

À partir du texte, de la géométrie et éventuellement de l'image des pages, produire :

- Le type probable du document.
- Les blocs de correction.
- Leur position exacte.
- Leur regroupement par question lorsque possible.
- Les avertissements utiles.
- L'indication qu'un mécanisme de secours est nécessaire lorsque la détection est trop incertaine.

### 12.2. Construire un moteur modulaire

Ne cherche pas immédiatement une règle universelle.

Construis plusieurs détecteurs spécialisés capables de reconnaître différentes conventions.

Pistes à explorer, à vérifier expérimentalement :

**Détection textuelle**

- Correction.
- Corrigé.
- Solution.
- Réponse.
- Answer.
- Solution de l'exercice.
- Autres marqueurs explicites pertinents.

**Détection structurelle**

- Titres de questions.
- Numérotation des exercices.
- Début et fin d'une correction.
- Corrections placées entre deux questions.
- Corrections regroupées à la fin.
- Corrections seules, organisées par question.

**Analyse géométrique**

- Reconstruction des lignes.
- Regroupement en paragraphes.
- Colonnes.
- Alignements.
- Espaces verticaux.
- Indentations.
- Positions relatives des questions et corrections.

**Analyse visuelle**

- Couleurs distinguant les réponses.
- Surlignages.
- Cases remplies de QCM.
- Symboles de correction.
- Autres conventions visuelles effectivement exploitables.

Ne suppose pas qu'une couleur, une police ou une position spatiale possède toujours une signification particulière.

Ces informations sont des indices, pas des preuves universelles.

### 12.3. Priorités de développement

P0 :

1. Construire une représentation exploitable des lignes et blocs.
2. Reconnaître les marqueurs explicites de questions et de corrections.

### 12.4. Règles importantes

Une absence de correspondance avec tes expressions régulières ne doit pas automatiquement conduire à classer un document comme statement_only.

Un document dont la structure est inconnue doit pouvoir être classé unknown.

Ne considère pas le mot « solution » au milieu d'une question comme un marqueur certain de correction.

Un même bloc peut couvrir plusieurs lignes, figures ou équations.

Ne masque pas uniquement les mots extraits du texte PDF lorsqu'une correction contient également des éléments graphiques.

Les zones ambiguës ne doivent pas donner lieu à une promesse de détection réussie.

Un faux négatif peut révéler une réponse. Un faux positif masque une question. Les deux erreurs sont importantes, avec une asymétrie particulière concernant les spoilers.

Couvre notamment :

- Question suivie de sa correction.
- Plusieurs questions et corrections alternées.
- Correction placée à droite d'une question.
- Corrigé regroupé en fin de document.
- Corrigé uniquement.
- Sujet uniquement.
- Document ambigu.
- Document sans texte extractible.
- Question contenant le mot « solution ».
- Correction s'étendant sur plusieurs pages.
- QCM avec convention de correction reconnaissable.

Teste ensuite le moteur sur de vrais PDF disponibles légalement.

N'annonce aucune performance universelle à partir de quelques documents.

Les tests doivent vérifier les régions produites, pas uniquement le type du document.

### 14.1. Philosophie UX

Unspoil est un outil simple.

L'utilisateur doit immédiatement comprendre ce qu'il peut faire.

Il ne faut pas créer un dashboard, une multiplication d'écrans ou une interface artificiellement sophistiquée.

Le PDF doit occuper la majeure partie de l'espace disponible.

Les interactions doivent être évidentes.

Les deux fonctionnalités essentielles sont :

- Masquer automatiquement les corrigés.
- Révéler progressivement le document lorsque nécessaire.

### 14.2. Interface principale

Développe une interface permettant :

- D'importer un PDF.
- D'accéder au lecteur.
- De déclencher le bouton « Masquer les corrigés ».
- D'afficher l'état du traitement.
- D'afficher les résultats ou les avertissements.
- D'accéder au mode de révélation progressive.

Les textes doivent être courts et compréhensibles.

Exemples :

- Masquer les corrigés.
- Afficher le corrigé.
- Remasquer le corrigé.
- Révélation progressive.
- Aucun corrigé n'a été détecté.

### 14.3. Moteur de masquage

À partir des CorrectionBlock retournés par Hazem :

- Positionner des rectangles blancs opaques sur le document.
- Associer les rectangles appartenant à un même bloc.
- Créer un bouton « Afficher le corrigé » par bloc.
- Gérer l'état masqué ou révélé de chaque bloc.
- Révéler uniquement le bloc choisi.
- Permettre son remasquage.

Un bloc constitué de plusieurs rectangles ou situé sur plusieurs pages doit rester une entité logique unique.

Le rendu du document ne doit pas être modifié.

Les masques doivent suivre les transformations du lecteur.

Utilise les conventions géométriques de Salif.

### 14.4. Mécanisme de secours

Il s'agit d'une fonctionnalité fondamentale, et non d'une amélioration facultative.

Développe immédiatement ce mécanisme, puisqu'il est indépendant du détecteur de Hazem.

Le document est couvert par un masque blanc opaque.

Une ligne horizontale manipulable délimite la partie visible et la partie cachée.

Lorsque l'utilisateur déplace cette ligne vers le bas, la partie située au-dessus apparaît.

Lorsqu'il remonte la ligne, le contenu est remasqué.

L'interaction doit être fluide.

Prends en compte :

- Les événements de pointeur.
- La souris.
- Le tactile.
- Le déplacement continu.
- Les limites de la page.
- Le zoom.
- Le défilement.
- Les documents multipages.

Proposition d'implémentation à évaluer : maintenir une frontière de révélation dans le repère du document, puis calculer pour chaque page la partie visible et la partie couverte.

Les pages situées avant cette frontière sont visibles ; celles situées après restent couvertes.

Tu peux choisir une implémentation plus simple si elle respecte le comportement attendu.

Évite qu'un défilement révèle automatiquement des pages qui devraient rester cachées.

### 14.5. Gestion des différents résultats du détecteur

Pour mixed :

- Afficher les questions.
- Masquer les blocs de correction.
- Permettre leur révélation individuelle.

Pour statement_only :

- Afficher « Aucun corrigé n'a été détecté ».
- Ne pas créer de masques arbitraires.

Pour correction_only :

- Maintenir les corrections couvertes.
- Permettre leur révélation par question.

Pour unknown :

- Afficher un avertissement.
- Proposer ou activer le mécanisme de secours.

Si needsFallback est vrai, présenter clairement la possibilité de révélation progressive.

Même lorsque le détecteur considère avoir reconnu un document, l'utilisateur doit pouvoir basculer manuellement vers le mode de secours.

### 14.6. Responsive design

L'expérience doit fonctionner sur ordinateur et téléphone.

Privilégie :

- Un document occupant la largeur disponible.
- Des boutons suffisamment grands au tactile.
- Une barre d'actions simple.
- Une interface lisible.
- Des contrastes suffisants.
- Une navigation clavier lorsque pertinente.

Ne produis pas une application mobile distincte.

L'interface responsive existante est celle de la PWA.

### 14.7. Développer sans attendre les autres

Utilise des données fictives représentant :

Développe le moteur de masquage et le mécanisme de secours indépendamment du vrai lecteur.

Utilise temporairement une page de démonstration ou un composant fictif reproduisant les dimensions d'une page.

Les mocks sont uniquement des outils de développement.

Ils ne doivent pas être présentés comme une détection automatique réelle.

Remplace-les par les résultats du vrai moteur lors de l'intégration.

### 14.8. Tests

Teste notamment :

- Le remasquage fonctionne.
